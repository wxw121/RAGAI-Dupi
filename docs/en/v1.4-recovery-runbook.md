## Offline Recovery ZIP workflow

Downloaded Recovery ZIP files are portable, offline copies. Restore does not read a local ZIP directly. Open the source knowledge base's **Recovery** tab and choose **Import ZIP**. The intake verifies the manifest checksum and summary, tenant and source knowledge-base identity, required restore items, the exact declared file set, and every file's size and SHA-256. Unsafe paths, duplicate or undeclared files, and suspicious compression ratios are rejected.

A successful intake returns `202 Accepted` with an operation job. Poll `GET /api/v1/operations/{jobId}` until it reaches `COMPLETED`; the publish transaction then writes the `RECOVERY_ARCHIVE_IMPORT` audit event and exposes the verified archive under a new internal archive ID. The original archive ID is never overwritten. Select Restore on that imported archive to create the normal hidden restore target. Its name includes the first eight archive ID characters and this restore's creation time as `yyyy-MM-dd HH:mm:ss.SSS UTC`, keeping repeated restores distinguishable.

New archives include `record:document-assets` metadata and one `asset:*` object per Markdown image. Restore verifies and remaps those objects into the target knowledge base. Older archives remain restorable, but images omitted by those archives cannot be reconstructed; create a new archive from the intact source knowledge base when full image recovery is required.

Invalid archives return `400`; requests beyond the multipart limit return `413`. Defaults allow a 1 GiB compressed ZIP, 8 GiB total uncompressed data, a 4 GiB single entry, 20,000 file entries, and a 100:1 compression ratio. Operators can tighten these limits with `DUPI_RECOVERY_MAX_IMPORT_*` and `DUPI_MULTIPART_MAX_*` environment variables.

## Durable operation and staging contract

Recovery ZIP import, Markdown package import, and knowledge-base deletion use the same durable operation API:

- creation returns `202 Accepted` and an operation job;
- `GET /api/v1/operations/{jobId}` requires `KB_READ` and reports `PREPARED`, `RUNNING`, `RETRY_WAIT`, `COMPENSATING`, `COMPLETED`, or `FAILED`, together with step progress;
- `POST /api/v1/operations/{jobId}/retry` requires `MAINTENANCE` plus `KB_READ` and is valid only for `FAILED` jobs;
- deleting a knowledge base first changes its lifecycle to `DELETING`, so normal reads cannot observe a partly deleted resource.

Before external staging I/O, the service persists an owner token, epoch, lease, and a unique attempt/object key. Flyway V28 adds `operation_staging_attempts`; its durable states are `ACTIVE`, `CLEANUP_PENDING`, and `CLEANED`. Lease takeover atomically makes the superseded owner's active attempts cleanup-pending. Retention moves abandoned, non-runnable intake to compensation, while a bounded replayer performs checked deletion. An absent object keeps cleanup truth pending, so a late writer is deleted on a later pass. `OPERATION_STAGING_RETENTION_HOURS` and `OPERATION_STAGING_CLEANUP_LIMIT` are both clamped to at least 1; the default cleanup schedule is hourly.

Markdown packages use the same staging protocol. Prepared document metadata is not visible through normal document APIs. All final objects are checksum-verified before one publish transaction makes every document visible and completes the operation; failure runs compensation rather than publishing a partial package.

## PostgreSQL V24 to V28 migration drill

Run this against an isolated Compose project. It creates a disposable database, applies the repository migrations through V24, then upgrades the same database through V28 and validates the schema history. The pinned Flyway image is deliberately independent from the API process so Hibernate cannot mask an incomplete migration.

```powershell
$project = "dupi-upgrade-v28"
$database = "dupi_rag_upgrade_verify"
$migrationPath = (Resolve-Path "services/api/src/main/resources/db/migration").Path
$network = "${project}_default"
if (-not $env:POSTGRES_PASSWORD) { throw "Set POSTGRES_PASSWORD to the value used by deploy/.env" }

docker compose -f deploy/docker-compose.yml -p $project up -d --wait postgres
docker compose -f deploy/docker-compose.yml -p $project exec -T postgres `
  psql -U dupi -d postgres -v ON_ERROR_STOP=1 -c "CREATE DATABASE $database"

docker run --rm --network $network `
  -v "${migrationPath}:/flyway/sql:ro" redgate/flyway:10.17.0 `
  -url="jdbc:postgresql://postgres:5432/$database" -user=dupi `
  -password="$env:POSTGRES_PASSWORD" -target=24 migrate

docker run --rm --network $network `
  -v "${migrationPath}:/flyway/sql:ro" redgate/flyway:10.17.0 `
  -url="jdbc:postgresql://postgres:5432/$database" -user=dupi `
  -password="$env:POSTGRES_PASSWORD" migrate
docker run --rm --network $network `
  -v "${migrationPath}:/flyway/sql:ro" redgate/flyway:10.17.0 `
  -url="jdbc:postgresql://postgres:5432/$database" -user=dupi `
  -password="$env:POSTGRES_PASSWORD" validate

docker compose -f deploy/docker-compose.yml -p $project exec -T postgres `
  psql -U dupi -d $database -v ON_ERROR_STOP=1 -c `
  "SELECT version, success FROM flyway_schema_history WHERE version IN ('24','25','26','27','28') ORDER BY installed_rank; SELECT to_regclass('public.operation_jobs'), to_regclass('public.operation_staging_attempts'); SELECT column_name FROM information_schema.columns WHERE table_name='rag_eval_cases' AND column_name IN ('expected_document_id','expected_document_ids') ORDER BY column_name;"
```

All five history rows must be successful; both relation names and both RAG evaluation document-ID columns must be present. Drop the disposable Compose project with `docker compose -f deploy/docker-compose.yml -p $project down -v` only after preserving the drill evidence.

## MinIO outage and restart drill

Use a disposable tenant and a unique `Idempotency-Key` for each intake. First run the normal Recovery rehearsal below. Then exercise each durable workflow while polling the returned operation ID:

1. Submit a knowledge-base delete, Recovery ZIP import, or Markdown package import and capture the `202` response. For intake failure before a response, keep the same idempotency key for the reopen attempt.
2. Stop object storage with `docker compose -f deploy/docker-compose.yml stop minio`; restart the API as well with `docker compose -f deploy/docker-compose.yml restart api` to prove the operation, steps, attempts, and leases are not process memory.
3. Start storage with `docker compose -f deploy/docker-compose.yml start minio`, wait for health, and poll `GET /api/v1/operations/{jobId}`. Automatic retry may pass through `RETRY_WAIT`; if the job exhausts its budget and becomes `FAILED`, call the retry endpoint once with an identity holding `MAINTENANCE` and `KB_READ`.
4. Require `COMPLETED`, or require compensation to finish before accepting `FAILED`. Verify that Markdown documents appear only after completion, a deleted knowledge base is unavailable from `DELETING` onward, and no operation-owned staging object remains after cleanup replay.
5. Repeat the intake with the same idempotency key. It must return the same logical operation or safely reopen it with a new staging owner/epoch; it must not duplicate an archive or Markdown document.

Deterministic unit tests cover the races that a manual container stop cannot time reliably: owner loss and heartbeat, lease takeover, late writer after cleanup, absent-object replay, old-job reopen, Recovery/Markdown publish fencing, and atomic Markdown visibility. The Compose drill remains necessary to prove PostgreSQL and MinIO persistence across real container restarts.

## Offline Recovery ZIP workflow

Downloaded Recovery ZIP files are portable, offline copies. Restore does not read a local ZIP directly. Open the source knowledge base's **Recovery** tab, choose **Import ZIP**, and wait for synchronous validation to complete. The import verifies the manifest checksum and summary, tenant and source knowledge-base identity, required restore items, the exact declared file set, and every file's size and SHA-256. Unsafe paths, duplicate or undeclared files, and suspicious compression ratios are rejected.

A successful import returns `201 Created`, writes a `RECOVERY_ARCHIVE_IMPORT` audit event, and stores the verified data under a new internal archive ID with status `COMPLETED`. The original archive ID is never overwritten. Select Restore on that imported archive to create the normal hidden restore target. Its name includes the first eight archive ID characters and this restore's creation time as `yyyy-MM-dd HH:mm:ss.SSS UTC`, keeping repeated restores distinguishable.

New archives include `record:document-assets` metadata and one `asset:*` object per Markdown image. Restore verifies and remaps those objects into the target knowledge base. Older archives remain restorable, but images omitted by those archives cannot be reconstructed; create a new archive from the intact source knowledge base when full image recovery is required.

Invalid archives return `400`; requests beyond the multipart limit return `413`. Defaults allow a 1 GiB compressed ZIP, 8 GiB total uncompressed data, a 4 GiB single entry, 20,000 file entries, and a 100:1 compression ratio. Operators can tighten these limits with `DUPI_RECOVERY_MAX_IMPORT_*` and `DUPI_MULTIPART_MAX_*` environment variables.

# V2.0 RAG Quality Closure Design

Updated: 2026-07-26

## Summary

V2.0 closes the selected RAG quality loop by turning every evaluation run into release evidence. The design deliberately uses the existing `RagEvalRun.metrics` JSON persistence and the existing Web RAG evaluation panel so the release can ship without a database migration.

## Goals

- Persist feedback candidates from failed or degraded eval signals as immutable run evidence.
- Add deterministic answer-quality judgement for groundedness, citation completeness, refusal/no-answer correctness, and hallucination risk.
- Summarize retrieval experiment dimensions from run evidence.
- Summarize data/index governance signals that explain source-coverage problems.
- Convert run metrics into SLO-style release objectives.
- Gate candidate profile promotion through canary promote/rollback logic.
- Emit a compact release report that references the evidence keys needed for sign-off.

## Non-goals

- No dedicated feedback workflow table, reviewer assignment queue, bulk promotion UI, or workflow history in V2.0.
- No production telemetry ingestion service, external alert routing, or tenant-wide always-on SLO backend.
- No optional LLM judge in the packaged V2.0 path.
- No full experiment registry lifecycle, ownership model, or winner-recommendation engine.
- No new database migration is required for the V2.0 closure MVP.

## Metrics contract

| Key | Purpose | Important fields |
| --- | --- | --- |
| `releaseReadiness` | Summarizes release status and evidence requirements | `version`, `status`, `readinessScore`, `blockerCount`, `requiredEvidence`, `artifactKeys`, `recommendedAction` |
| `realQueryFeedback` | Stores feedback candidates as immutable snapshots | `candidateCount`, `candidates`, `categoryBreakdown` |
| `experimentMatrix` | Captures experiment dimensions observed in the run | `topKValues`, `profiles`, `retrievalModes`, `caseCount`, `evaluationCount`, `rerankEvidenceCount` |
| `answerQuality` | Provides deterministic answer risk evidence | `judgeStatus`, `riskCases`, `groundedPassRate`, `hallucinationRiskCount`, `unsupportedAnswerRiskCount` |
| `onlineObservability` | Summarizes fallback/no-answer/latency/profile-regression observations | `fallbackRate`, `latencyP95Ms`, `degradedProfileCount`, `sloStatus` |
| `dataIndexGovernance` | Explains corpus/index evidence quality | `expectedSourceCoverageRate`, `missingSourceCount`, `multiDocumentCaseCount`, `ambiguousCaseCount`, `embeddingDimensions`, `governanceStatus` |
| `onlineSlo` | Converts run evidence into release objectives | `status`, `objectives`, `breachedObjectives`, `observed` |
| `canaryGate` | Decides candidate profile promotion/rollback | `baselineProfile`, `candidateProfiles`, `profileGateStatuses`, `decision`, `reasons`, `shadowEvalRequired`, `rollbackPlan` |
| `v2QualityClosure` | Summarizes closure state and completed capabilities | `status`, `completedCapabilities`, `recommendedActions` |
| `releaseReport` | Gives the release recommendation and evidence list | `releaseName`, `releaseGateStatus`, `canaryDecision`, `closureStatus`, `recommendedAction`, `evidenceKeys` |

## Key rules

- Feedback candidates are generated only for failed cases, citation-eligible citation failures, or meaningful fallback signals. A literal `fallbackReason=none` does not create a candidate.
- Candidate IDs include persisted result identity when available and otherwise include run/profile/case identity to avoid collisions in multi-profile runs.
- Correct citation-ineligible hard-negative/no-answer cases do not count as hallucination risk.
- Canary promotion requires candidate profiles. A classic-only run is release evidence but not a canary promotion candidate.
- Canary promotion also honors actual profile gate decisions through `profileGateStatuses`; a blocked profile gate causes rollback even if aggregate eval metrics pass.

## Web design

The RAG evaluation panel keeps the existing Quality dashboard layout and adds V2.0 cards for closure, online SLO, and canary gate status. Existing cards default to the V2.0 version label and surface the new detail fields without introducing a separate workflow screen.

## Seal criteria

V2.0 can be sealed when API/Web metadata is `2.0.0`, the documents in this release are present, the metrics contract is implemented and tested, Web cards render the new evidence, and the final verification gates pass.

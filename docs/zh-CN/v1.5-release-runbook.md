# V1.5.0 RAG 质量升级发布手册

<!-- language-switch -->
[English](../en/v1.5-release-runbook.md) | **中文**

> **中文说明：** 本手册规定 V1.5.0 RAG 质量升级的兼容性要求、发布前检查、部署步骤、质量门禁、回滚方案和最终发布证据。

**状态：** 待发布。只有本文中的最终门禁全部在发布提交上通过，且合并后的 `main` CI 为绿色，才能创建 `v1.5.0` 标签。

## 范围

V1.5.0 增加知识库级 `CLASSIC`、`PARENT_CHILD`、`QA_ASSISTED` 和 `COMBINED` 检索配置，但不替换现有 `VECTOR`、`HYBRID` 和 `RERANK` 执行模式。Worker 摄取会构建可过滤的 Profile V2 超集，其中包含原始、父级、子级和 QA 条目。只有当前索引修订版的候选配置通过相对于 `CLASSIC` 的质量门禁后，非经典配置才能成为知识库默认值。

## 兼容性

- 未选择检索配置的现有请求继续使用 `CLASSIC`。
- `VECTOR`、`HYBRID` 和可选 Rerank 保持现有 API 行为。
- QA 生成失败不会导致源文档摄取失败。
- 配置选择只改变检索入口路由，不会重建已经存在的 Profile V2 索引。
- 恢复后的知识库通过 V1.4 恢复契约保留 Profile collection 数据、门禁状态和切换状态。

## 发布前检查

1. 在应用 Flyway V18-V20 前备份 PostgreSQL、MinIO 和 Milvus。V18 增加检索索引 schema；V19 增加 Profile V2 修订版、就绪状态和评估证据；V20 保存 Profile V2 切换状态。
2. 记录每个知识库的文档数、完成文档数、当前默认配置、活动检索 Profile、索引修订版和当前 Milvus collection 计数。
3. API 和 Worker 必须配置相同且非空的 `MILVUS_PROFILE_COLLECTION`。它不能复用 `MILVUS_COLLECTION`，也不能复用其他环境的 collection。
4. 确认 Milvus 在一次性迁移期间有足够容量保存原始/父级/子级/QA 超集，以及切换前的临时 Legacy 双写数据。
5. 首次发布保持 `COMBINED_CHILD_WEIGHT=1.0` 和 `COMBINED_QA_WEIGHT=0.8`，除非已有保存的基准证明其他值更优。
6. API 和 Worker 必须使用相同且非空的 `DUPI_INTERNAL_KEY`。确认 QA 生成使用的 LLM 端点可达，但不要仅因 QA 生成不可用而阻止发布。
7. 所有现有知识库继续使用 `CLASSIC`，直到 Profile V2 索引就绪且当前修订版通过质量门禁。

## 发布步骤

1. 先部署 PostgreSQL/Flyway 和 API。启动 Worker 前，验证 `/actuator/health`、Flyway V18-V20 和现有知识库列表。
2. 使用 `MILVUS_PROFILE_COLLECTION`、组合权重和现有可靠队列设置部署 Worker。知识库完成 Profile V2 切换前，新摄取继续双写 Legacy 原始向量。
3. API 和 Worker 健康后部署 Web。在迁移数据前，验证知识库设置页和 RAG 评估面板能够加载。
4. 选择一个非关键知识库并执行重建索引。重建按文档滚动替换；不要先删除 Profile V2 collection 或清空全部活动 chunk。
5. 等待所有文档变为 `COMPLETED` 且 `index_schema_version=2`。清理切换前，确认 Profile V2 已就绪、`index_revision` 非空，并核对原始/父级/子级/QA 条目数。
6. 为 `CLASSIC` 和每个候选配置运行至少三个可引用的评估用例。候选配置不得降低命中率或引用通过率，结果必须引用当前索引修订版。
7. 只有非经典配置的决策为 `PASSED` 时才能激活。`BLOCKED`、`INSUFFICIENT_DATA`、`STALE`、`INDEX_NOT_READY` 和 `not_evaluated` 都是硬阻断；被阻止的激活由 API 返回 `409 retrieval_profile_gate_blocked`。
8. 每次只扩展一个知识库。先使用 `PARENT_CHILD`；只有保存的评估证据证明有收益时，才启用 `QA_ASSISTED` 或 `COMBINED`。

## 验收检查

- API、Worker、Web 测试和 Web 生产构建必须基于同一发布差异通过。
- JaCoCo 行覆盖率保持在配置的 95% 阈值或以上。
- Pester 发布契约、脱敏 Compose 配置、`git diff --check`、依赖审计、SBOM/许可证策略、Trivy 策略、非 root 运行时探针和镜像大小预算全部通过。
- Canary 知识库在激活任何非经典配置前达到 100% Profile V2 文档就绪，并返回与 `CLASSIC` 等价的结果。
- 候选 Profile 必须具有当前修订版的 `PASSED` 证据，且命中率和引用质量不回归。
- 热态 P95 延迟不超过保留生产基线的 1.25 倍，且 fallback 率不增加。

## 监控

- 对 `index_schema_version<2` 的文档、过期索引修订版、非 `PASSED` 门禁决策、Profile V2 清理失败和重建索引期间的摄取失败发出告警。
- 跟踪 Profile V2 collection 增长、QA 条目数、QA 生成失败、检索 fallback 原因、Rerank fallback、命中率、引用通过率和各 Profile 的 P95 延迟。
- 保留发布扫描、Canary 评估 run ID、索引修订版、collection 计数和已脱敏的回滚结果。

## 回滚

1. 将知识库默认配置切回 `CLASSIC`；此操作无条件执行，不需要候选门禁证据。
2. 调查候选质量或延迟回归时，不要删除 Profile V2 collection。它是四种 Profile 和可重复评估的共享数据源。
3. 如果 Worker 在 Profile V2 切换前发布失败，停止 Worker，保留可靠 processing queue，恢复发布版 Worker，并从持久化文档/索引状态继续。
4. API 或数据库故障优先采用向前修复。V18-V20 只做新增，但手动修改 `profile_index_activated`、`index_revision` 或文档 schema version 可能重新启用无效 fallback 路径。
5. Legacy 清理后，回滚到只理解 Legacy collection 的代码需要经过验证的归档/恢复或完整重建索引。不要清除持久化切换状态以强制 fallback。
6. 先回滚 Web，再回滚 Worker；只有确认旧组件理解当前队列载荷和数据库 schema 后，才能回滚 API。

## 发布边界

只有最终门禁证据记录完成后，发布分支才可以合并。从已验证且合并后的 `main` 提交创建带注释的 `v1.5.0` 标签，然后发布 GitHub Release 说明，并链接本手册及迁移、门禁和回滚要求。

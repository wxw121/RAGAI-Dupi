# V1.4.1 上传治理发布手册

<!-- language-switch -->
[English](../en/v1.4.1-release-runbook.md) | **中文**

> **中文说明：** 本手册介绍 V1.4.1 上传治理版本的发布前检查、上线步骤、验证与回滚要求，覆盖配额、幂等、任务取消、过期回调防护及失败通知。

## 范围

V1.4.1 增加持久化上传配额预留、单文件幂等、可靠的摄取执行/ACK 行为、取消、过期回调保护、终态失败 Webhook 投递和受治理的 Web 上传。V1.4.0 恢复归档保持不变。

## 发布前检查

1. 在应用 Flyway V17 前备份 PostgreSQL。V17 创建 `upload_quota_reservations`、`upload_window_events` 和 `ingest_failure_notifications`，为 `documents` 增加 `quota_reservation_id`，并为 `ingest_jobs` 增加执行与租约字段。
2. 确认 Redis 对就绪队列和 `INGEST_PROCESSING_QUEUE` 都有足够容量。
3. 配置 README 中记录的配额变量。默认值为每个租户/用户保留 1 GiB、1,000 个文档，以及每小时滚动窗口 256 MiB。保留用量统计活动的 `PENDING + COMMITTED` 预留；`RELEASED` 不再占用配额。
4. 如需外部失败告警，配置 `INGEST_FAILURE_NOTIFICATION_WEBHOOK_URL`；留空时跳过投递。根据目标端点调整 `INGEST_FAILURE_NOTIFICATION_TIMEOUT_SECONDS`、`INGEST_FAILURE_NOTIFICATION_MAX_ATTEMPTS` 和 `INGEST_FAILURE_NOTIFICATION_DISPATCH_CRON`。
5. 共享环境中的 API 和 Worker 必须使用相同且非空的 `DUPI_INTERNAL_KEY`。
6. 发布期间不要删除 processing list。它是任务已经离开就绪队列但尚未最终确认的恢复证据。

## 发布步骤

1. 先部署 PostgreSQL/Flyway 和 API。
2. 使用拥有 `DOCUMENT_UPLOAD` 权限的账户验证 `GET /actuator/health` 和 `GET /api/v1/upload-quota`。
3. 使用正确的 `INGEST_PROCESSING_QUEUE`、`INGEST_LEASE_SECONDS` 和唯一 `WORKER_ID` 部署 Worker。
4. API 和 Worker 健康后再部署 Web。
5. 使用 `Idempotency-Key` 上传一个小文档；使用相同请求重放，并确认返回同一文档和当前任务。
6. 使用相同密钥上传不同内容并确认返回 409；上传超大文件确认返回 413；耗尽窗口配额确认返回 429 和 `Retry-After`。
7. 分别取消一个排队任务和一个运行中任务。排队任务应变为 `CANCELLED`；运行中任务应从 `CANCEL_REQUESTED` 变为 `CANCELLED`，且不产生失败通知。
8. 重试失败任务并确认 `executionId` 已改变。发送旧 execution 或重复 sequence 回调，确认 HTTP 200 且响应包含 `ignored=true`。
9. 配置 `INGEST_FAILURE_NOTIFICATION_WEBHOOK_URL` 后，制造一个 `FAILED` 摄取并确认 Webhook 投递。重复终态回调不得创建第二个事件；Webhook 投递失败应从 `FAILED` 重试，最终进入 `EXHAUSTED`。

## 运维检查

- 将 `retainedBytesUsed` 和 `retainedDocumentsUsed` 与活动的 `PENDING + COMMITTED` 预留及现存文档比较；手动修改配额总量前，应把旧 `PENDING` 预留纳入对账。
- 手动修改配额总量前，调查旧 `PENDING` 预留和旧 processing-list 消息。
- `CANCEL_REQUESTED` 任务应继续轮询，直到 Worker 返回 `CANCELLED`。
- `ingest_failure_notifications.event_key` 唯一。重复回调不得创建新记录；Webhook 投递从 `PENDING`/`FAILED` 记录重试，直到 `DELIVERED` 或 `EXHAUSTED`。
- 恢复操作应为已恢复文档创建 `COMMITTED` 预留；放弃恢复时，应以 `Recovery restore abandoned` 原因释放关联预留。
- Web transport abort 只停止当前 HTTP 上传。如果响应已经创建文档或任务，应调用摄取取消端点。

## 回滚

1. 先回滚 Web；批量上传 API 保持可用，以维持兼容性。
2. 回滚 API 前先停止 Worker，避免 V1.4.1 的 claim/lease/callback 契约发送到旧 API。
3. API 或数据库问题优先采用向前修复。V17 只做新增，但删除相关表或字段会破坏配额和执行证据。
4. 如果 Worker 发布失败，保留 processing list，恢复 V1.4.1 Worker，并由 PostgreSQL 中的执行/租约状态决定任务是否可以继续。

## 发布边界

只有最终差异通过上述全部门禁后，才允许在本地合并或打标签。远程推送、创建 Pull Request 或远程标签需要明确授权，因为这些操作会把工作区代码发布到外部。

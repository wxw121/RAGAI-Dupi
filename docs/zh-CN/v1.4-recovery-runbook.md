# V1.4 恢复手册

> **中文说明：** 本手册说明 V1.4.0 知识库归档与恢复的存储、权限、操作流程和验证要求。英文内容为规范正文，本说明用于帮助中文读者快速确认操作边界。

## 范围

V1.4.0 可以归档和恢复单个知识库，包括源对象、关系型记录、评估/检索配置以及 Dense/Sparse 向量载荷。它不提供 PostgreSQL PITR、跨区域复制或计划保留策略。

## 存储与访问

使用专用的私有 MinIO Bucket，默认名称为 `dupi-recovery`。API 凭证需要同时拥有文档 Bucket 和恢复 Bucket 的读取、写入、列举和删除权限；两个 Bucket 都不能公开。规范对象位于 `archives/{tenantId}/{archiveId}/` 下。下载的 ZIP 文件是可离线保管和迁移的传输副本；Restore 不会直接读取本地 ZIP，必须先用 **Import ZIP** 校验并导入为新的内部归档。

存储容量应同时考虑保留的源对象、序列化记录/向量，以及并发归档所需的余量。归档仍需按业务保留策略明确删除；导入过程中遗留的 staging 则由独立的租约、保留期与 cleanup replayer 自动收敛。

## 操作流程

1. 打开知识库并选择 **Recovery**。
2. 创建归档。系统会阻止新的变更，并等待活动摄取、评估和稀疏迁移任务进入静止状态。
3. 等待状态变为 `COMPLETED`；检查条目数、字节数和清单校验和。新归档会包含 `record:document-assets` 记录及逐个 `asset:*` 图片对象。失败时重试。只有完整归档才能下载。
4. 需要使用离线 ZIP 时，在同一知识库的 Recovery 页面点击 **Import ZIP**。系统会验证清单自身校验和、租户和源知识库、必需条目、声明文件集合，以及每个文件的大小和 SHA-256；不接受损坏、缺失、多余、跨目录或压缩比异常的内容。
5. intake 成功返回包含 operation job 的 `202 Accepted`。轮询 `GET /api/v1/operations/{jobId}`；只有操作变为 `COMPLETED` 后，新内部归档才可见，原 ZIP 中的归档 ID 不会被复用或覆盖，同时会留下 `RECOVERY_ARCHIVE_IMPORT` 审计记录。
6. 恢复已完成的归档。目标知识库在 `RESTORING` 状态下保持隐藏；名称会拼接 Archive ID 前 8 位和本次 Restore 创建时间（`yyyy-MM-dd HH:mm:ss.SSS UTC`），重试时继续使用同一恢复目标。
7. 只有状态变为 `COMPLETED` 后才能打开目标链接。放弃失败恢复时应删除目标。

导入会先完成输入校验与耐久化 staging，再返回 `202 Accepted`；格式或校验失败返回 `400`，超过 API multipart 上限返回 `413`。默认允许 1 GiB 压缩 ZIP、8 GiB 解压后总量、4 GiB 单条目、20,000 个文件和最高 100 倍压缩比，均可通过 `DUPI_RECOVERY_MAX_IMPORT_*` 和 `DUPI_MULTIPART_MAX_*` 环境变量收紧。

## 持久化操作与 staging 契约

Recovery ZIP 导入、Markdown 包导入和知识库删除共用操作 API：创建返回 `202 Accepted`；具有 `KB_READ` 权限时通过 `GET /api/v1/operations/{jobId}` 查看 `PREPARED`、`RUNNING`、`RETRY_WAIT`、`COMPENSATING`、`COMPLETED`、`FAILED` 及步骤进度；只有 `FAILED` 能调用 `POST /api/v1/operations/{jobId}/retry`，且调用者必须同时具有 `MAINTENANCE` 和 `KB_READ`。删除开始时知识库先进入 `DELETING`，避免正常读取观察到半删除资源。

外部 staging I/O 开始前，服务会持久化 owner token、epoch、lease 和唯一 attempt/object key。Flyway V28 新增 `operation_staging_attempts`，状态为 `ACTIVE`、`CLEANUP_PENDING`、`CLEANED`。租约接管会在同一事务中把被替代 owner 的 active attempts 转为待清理；保留扫描把遗弃且不可运行的 intake 转入补偿，有界 replayer 执行 checked delete。对象暂时不存在时不会丢弃 cleanup truth，writer 迟到后仍会在后续轮次删除。`OPERATION_STAGING_RETENTION_HOURS` 与 `OPERATION_STAGING_CLEANUP_LIMIT` 都至少按 1 处理，默认每小时扫描。

Markdown 包也使用同一协议。prepared 文档元数据不会从正常文档 API 可见；所有最终对象通过校验后，由一个 publish 事务同时公开全部文档并完成操作，失败则补偿，不会暴露部分包。

## PostgreSQL V24 → V28 演练

在隔离的 Compose project 中执行以下命令。它会创建一次性数据库，先应用到 V24，再对同一个数据库升级至 V28 并执行 Flyway validate；独立 Flyway 容器可避免 Hibernate 掩盖缺失迁移。

```powershell
$project = "dupi-upgrade-v28"
$database = "dupi_rag_upgrade_verify"
$migrationPath = (Resolve-Path "services/api/src/main/resources/db/migration").Path
$network = "${project}_default"
if (-not $env:POSTGRES_PASSWORD) { throw "请把 POSTGRES_PASSWORD 设为 deploy/.env 使用的值" }
docker compose -f deploy/docker-compose.yml -p $project up -d --wait postgres
docker compose -f deploy/docker-compose.yml -p $project exec -T postgres psql -U dupi -d postgres -v ON_ERROR_STOP=1 -c "CREATE DATABASE $database"
docker run --rm --network $network -v "${migrationPath}:/flyway/sql:ro" redgate/flyway:10.17.0 -url="jdbc:postgresql://postgres:5432/$database" -user=dupi -password="$env:POSTGRES_PASSWORD" -target=24 migrate
docker run --rm --network $network -v "${migrationPath}:/flyway/sql:ro" redgate/flyway:10.17.0 -url="jdbc:postgresql://postgres:5432/$database" -user=dupi -password="$env:POSTGRES_PASSWORD" migrate
docker run --rm --network $network -v "${migrationPath}:/flyway/sql:ro" redgate/flyway:10.17.0 -url="jdbc:postgresql://postgres:5432/$database" -user=dupi -password="$env:POSTGRES_PASSWORD" validate
docker compose -f deploy/docker-compose.yml -p $project exec -T postgres psql -U dupi -d $database -v ON_ERROR_STOP=1 -c "SELECT version, success FROM flyway_schema_history WHERE version IN ('24','25','26','27','28') ORDER BY installed_rank; SELECT to_regclass('public.operation_jobs'), to_regclass('public.operation_staging_attempts'); SELECT column_name FROM information_schema.columns WHERE table_name='rag_eval_cases' AND column_name IN ('expected_document_id','expected_document_ids') ORDER BY column_name;"
```

V24—V28 的五条 history 必须全部成功，两个 relation 和两个评估 document-ID 列必须存在。保存证据后，才可用 `docker compose -f deploy/docker-compose.yml -p $project down -v` 删除一次性环境。

## MinIO 故障与重启演练

使用一次性租户，并为每次 intake 设置唯一 `Idempotency-Key`。先执行下方正常 Recovery 演练，再验证每类耐久工作流：

1. 提交知识库删除、Recovery ZIP 导入或 Markdown 包导入并保存 `202` 中的 operation ID；如果 intake 在返回响应前失败，重开时必须沿用同一个幂等键。
2. 执行 `docker compose -f deploy/docker-compose.yml stop minio`，并用 `docker compose -f deploy/docker-compose.yml restart api` 验证 operation、step、attempt 与 lease 不依赖进程内存。
3. 执行 `docker compose -f deploy/docker-compose.yml start minio`，健康后继续轮询操作。自动重试可能经过 `RETRY_WAIT`；耗尽预算进入 `FAILED` 时，仅用同时具有 `MAINTENANCE` 与 `KB_READ` 的身份调用一次 operation retry。
4. 要求操作 `COMPLETED`，或要求补偿完成后才接受 `FAILED`。Markdown 文档只能在完成后整体可见；知识库从 `DELETING` 起必须不可读；cleanup replay 后不得残留 operation staging 对象。
5. 用同一幂等键重放 intake：必须返回同一逻辑操作，或以新 owner/epoch 安全重开，不能重复产生归档或 Markdown 文档。

现有确定性单元测试覆盖手工停容器难以稳定命中的竞态：owner loss/heartbeat、lease takeover、cleanup 后 writer 迟到、对象暂时不存在的 replay、旧 job reopen、Recovery/Markdown publish fencing 及 Markdown 原子可见性。Compose 演练仍负责证明真实 PostgreSQL、MinIO 容器重启后的持久性。

兼容说明：修复前生成的旧归档仍可恢复，但其中没有图片资产，系统无法从旧 ZIP 中补回未归档的图片。需要完整图片恢复时，应在升级后从仍保留图片的源知识库重新创建归档。

不要在工单或审计说明中记录对象密钥、向量、签名 URL、凭证或未经处理的供应商错误。恢复错误必须经过脱敏。

## 演练

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "Import-Module Pester; Invoke-Pester scripts/tests/rehearse-v1.4-recovery.Tests.ps1"
$corruptObject = {
  param($objectKey)
  docker run --rm --network deploy_default --entrypoint /bin/sh `
    -e "MC_ACCESS=$env:MINIO_ACCESS_KEY" -e "MC_SECRET=$env:MINIO_SECRET_KEY" -e "MC_OBJECT=$objectKey" minio/mc `
    -c 'mc alias set local http://minio:9000 "$MC_ACCESS" "$MC_SECRET" >/dev/null && printf corrupted-recovery-object | mc pipe "local/dupi-recovery/$MC_OBJECT" >/dev/null'
  return ($LASTEXITCODE -eq 0)
}.GetNewClosure()
& scripts/rehearse-v1.4-recovery.ps1 `
  -BaseUrl http://localhost:8080 `
  -ApiKey $env:DUPI_API_KEY `
  -FixtureFiles examples/sample-knowledge.md,examples/sample-knowledge.md `
  -CorruptObject $corruptObject
```

发布证据写入 `artifacts/v1.4-recovery/rehearsal.json`。它必须记录至少两个文档、归档条目数/字节数/校验和、对象/记录/向量验证、检索对比、损坏阻断、持续时间和清理结果。每个证据标志都必须为真，否则脚本以非零状态退出。仅执行策略测试、未提供 `CorruptObject` 的运行或仅发现 Playwright 测试，都不能作为发布证据。

2026-07-16 的最终 Compose 演练归档了 2 个文档，共 9 个条目、10,946 字节，并通过对象/向量校验和重算、恢复记录计数、检索等价性、规范对象损坏拒绝和范围清理验证。证据记录 `corruptionBlocked=true`。

## 发布扫描

从仓库根目录构建并扫描最终 Worker 镜像：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/scan-release.ps1 `
  -Image dupi-rag-worker:v1.4 `
  -OutputPath artifacts/v1.4-release-scan `
  -HighExceptionPath deploy/release-exceptions/v1.4.0.json
```

镜像必须通过 `pip check`，能够导入真实 Worker/PyMilvus 运行栈，使用 CPU-only PyTorch，以 UID/GID `65534` 运行，保持在 3 GiB 预算以内，生成 pip-audit、CycloneDX/Syft SBOM、Trivy 和 summary 证据，并通过应用依赖许可证拒绝清单。PyMilvus 2.5.18 保持在 Milvus 2.5 客户端系列，同时移除已弃用的 `pkg_resources` 依赖，以支持已修补的打包工具链。

扫描可以使用 `PATH` 中的 `pip-audit`，也可以回退到 `python -m pip_audit`。`deploy/release-exceptions/v1.4.0.json` 必须声明规范化镜像版本，并且只能包含没有上游修复版本的精确包/CVE 匹配；清单于 2026-08-15 到期。新增、可修复、非活动、不匹配、版本错误或过期的发现都会阻止发布。仅在本地 Trivy 数据库已经单独刷新并验证后，才允许使用 `-TrivySkipDbUpdate`。

2026-07-17 的最终发布扫描检查了 634,098,035 字节的镜像，发现 3 个 CRITICAL、19 个 HIGH 的 Trivy 问题和 1 个 pip-audit 问题；全部 23 项都包含在有日期限制的例外清单中。证据位于 `summary.md`、`worker-trivy.json` 和 `trivy-version.json`。应保留镜像摘要和漏洞数据库时间戳，不要硬编码可能因 BuildKit 重新生成来源而变化的摘要。运行时验证记录 `uid=65534`、`gid=65534`、`torch=2.10.0+cpu`、`pymilvus=2.5.18` 和 `cuda=False`。

## 故障处理

- 静止等待超时：让活动任务完成，诊断卡住的任务，然后重试同一归档。
- 超出容量：降低并发任务数；只有测量依赖和内存负载后才能提高配置上限。
- 归档校验失败：不要执行恢复。保留证据，直到完成诊断。
- 恢复验证失败：目标知识库保持隐藏。修复依赖后重试同一任务，或者放弃恢复。
- 放弃操作部分失败：只要仍有对象、记录或向量残留，就不能报告清理完成。

Flyway V15 和 V16 会级联清理已完成恢复的任务和恢复条目，并显式删除归档。依赖归档保留清理前，必须先应用这两个迁移。

## 基础设施备份

应用层恢复只是其中一层。生产环境仍然需要相互独立、经过恢复验证并在主机外保留的 PostgreSQL、MinIO Bucket、etcd 和 Milvus 备份。加密密钥和凭证应通过 Secret 管理，绝不能写入演练证据。

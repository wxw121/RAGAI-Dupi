# V1.4 恢复手册

<!-- language-switch -->
[English](../en/v1.4-recovery-runbook.md) | **中文**

> **中文说明：** 本手册说明 V1.4.0 知识库归档与恢复的存储、权限、操作流程和验证要求。英文内容为规范正文，本说明用于帮助中文读者快速确认操作边界。

## 范围

V1.4.0 可以归档和恢复单个知识库，包括源对象、关系型记录、评估/检索配置以及 Dense/Sparse 向量载荷。它不提供 PostgreSQL PITR、跨区域复制或计划保留策略。

## 存储与访问

使用专用的私有 MinIO Bucket，默认名称为 `dupi-recovery`。API 凭证需要同时拥有文档 Bucket 和恢复 Bucket 的读取、写入、列举和删除权限；两个 Bucket 都不能公开。规范对象位于 `archives/{tenantId}/{archiveId}/` 下。下载的 ZIP 文件只是传输视图，不是规范存储。

存储容量应同时考虑保留的源对象、序列化记录/向量，以及并发归档所需的余量。归档达到规定保留期后应明确删除；V1.4.0 不包含自动保留调度器。

## 操作流程

1. 打开知识库并选择 **Recovery**。
2. 创建归档。系统会阻止新的变更，并等待活动摄取、评估和稀疏迁移任务进入静止状态。
3. 等待状态变为 `COMPLETED`；检查条目数、字节数和清单校验和。失败时重试。只有完整归档才能下载。
4. 恢复已完成的归档。目标知识库在 `RESTORING` 状态下保持隐藏；重试时继续使用同一恢复目标。
5. 只有状态变为 `COMPLETED` 后才能打开目标链接。放弃失败恢复时应删除目标。

不要在工单或审计说明中记录对象密钥、向量、签名 URL、凭证或未经处理的供应商错误。恢复错误必须经过脱敏。

## 演练

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -Command "Import-Module Pester; Invoke-Pester scripts/tests/rehearse-v1.4-recovery.Tests.ps1"
$corruptObject = {
  param($objectKey)
  docker run --rm --network deploy_default --entrypoint /bin/sh `
    -e "MC_ACCESS=$env:MINIO_ACCESS_KEY" -e "MC_SECRET=$env:MINIO_SECRET_KEY" -e "MC_OBJECT=$objectKey" minio/mc `
    -c 'mc alias set local http://minio:9000 "$MC_ACCESS" "$MC_SECRET" >/dev/null && printf corrupted-recovery-object | mc pipe "local/dupi-recovery/$MC_OBJECT" >/dev/null'
  return ($LASTEXITCODE -eq 0)
}.GetNewClosure()
& scripts/rehearse-v1.4-recovery.ps1 `
  -BaseUrl http://localhost:8080 `
  -ApiKey $env:DUPI_API_KEY `
  -FixtureFiles examples/sample-knowledge.md,examples/sample-knowledge.md `
  -CorruptObject $corruptObject
```

发布证据写入 `artifacts/v1.4-recovery/rehearsal.json`。它必须记录至少两个文档、归档条目数/字节数/校验和、对象/记录/向量验证、检索对比、损坏阻断、持续时间和清理结果。每个证据标志都必须为真，否则脚本以非零状态退出。仅执行策略测试、未提供 `CorruptObject` 的运行或仅发现 Playwright 测试，都不能作为发布证据。

2026-07-16 的最终 Compose 演练归档了 2 个文档，共 9 个条目、10,946 字节，并通过对象/向量校验和重算、恢复记录计数、检索等价性、规范对象损坏拒绝和范围清理验证。证据记录 `corruptionBlocked=true`。

## 发布扫描

从仓库根目录构建并扫描最终 Worker 镜像：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/scan-release.ps1 `
  -Image dupi-rag-worker:v1.4 `
  -OutputPath artifacts/v1.4-release-scan `
  -HighExceptionPath deploy/release-exceptions/v1.4.0.json
```

镜像必须通过 `pip check`，能够导入真实 Worker/PyMilvus 运行栈，使用 CPU-only PyTorch，以 UID/GID `65534` 运行，保持在 3 GiB 预算以内，生成 pip-audit、CycloneDX/Syft SBOM、Trivy 和 summary 证据，并通过应用依赖许可证拒绝清单。PyMilvus 2.5.18 保持在 Milvus 2.5 客户端系列，同时移除已弃用的 `pkg_resources` 依赖，以支持已修补的打包工具链。

扫描可以使用 `PATH` 中的 `pip-audit`，也可以回退到 `python -m pip_audit`。`deploy/release-exceptions/v1.4.0.json` 必须声明规范化镜像版本，并且只能包含没有上游修复版本的精确包/CVE 匹配；清单于 2026-08-15 到期。新增、可修复、非活动、不匹配、版本错误或过期的发现都会阻止发布。仅在本地 Trivy 数据库已经单独刷新并验证后，才允许使用 `-TrivySkipDbUpdate`。

2026-07-17 的最终发布扫描检查了 634,098,035 字节的镜像，发现 3 个 CRITICAL、19 个 HIGH 的 Trivy 问题和 1 个 pip-audit 问题；全部 23 项都包含在有日期限制的例外清单中。证据位于 `summary.md`、`worker-trivy.json` 和 `trivy-version.json`。应保留镜像摘要和漏洞数据库时间戳，不要硬编码可能因 BuildKit 重新生成来源而变化的摘要。运行时验证记录 `uid=65534`、`gid=65534`、`torch=2.10.0+cpu`、`pymilvus=2.5.18` 和 `cuda=False`。

## 故障处理

- 静止等待超时：让活动任务完成，诊断卡住的任务，然后重试同一归档。
- 超出容量：降低并发任务数；只有测量依赖和内存负载后才能提高配置上限。
- 归档校验失败：不要执行恢复。保留证据，直到完成诊断。
- 恢复验证失败：目标知识库保持隐藏。修复依赖后重试同一任务，或者放弃恢复。
- 放弃操作部分失败：只要仍有对象、记录或向量残留，就不能报告清理完成。

Flyway V15 和 V16 会级联清理已完成恢复的任务和恢复条目，并显式删除归档。依赖归档保留清理前，必须先应用这两个迁移。

## 基础设施备份

应用层恢复只是其中一层。生产环境仍然需要相互独立、经过恢复验证并在主机外保留的 PostgreSQL、MinIO Bucket、etcd 和 Milvus 备份。加密密钥和凭证应通过 Secret 管理，绝不能写入演练证据。
